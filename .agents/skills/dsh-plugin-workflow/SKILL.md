# DSH 插件仓库：协作与发版流程

本技能只管**流程**：怎么开分支、怎么提交、Issue/PR 写什么、怎么发版。
**问题怎么定位**（哪个 API 漂移了、为什么插件加载失败）属于领域技能，例如 `dsh-plugin-compat-repair`（DSH 插件升级后加载失败）。

> 一条贯穿全流程的纪律：**验收由作者收口**。不要把"需要别人确认"的事项留在 PR 里当未勾选项。

## 1. 开工

1. 从 `main` 切分支，名字体现意图：
   - `fix/<主题>`（如 `fix/dsh-0.2-compat`）
   - `feat/<主题>`、`docs/<主题>`、`chore/<主题>`
2. 先跑一遍仓库自检，确认起点是干净的：
   ```sh
   npm run check        # 静态契约检查（若仓库提供）
   git status --short
   ```
3. 涉及运行时行为的改动，先想清楚**怎么证明它有效**；证据要在动手前就设计好，不要事后补。

## 2. 提交

- **按主题分组**，一个提交一件事。参考前缀：`fix(deps)` / `fix(api)` / `refactor(config)` / `test(contract)` / `docs` / `chore(release)`。
- 提交正文写清**为什么**（机制、失败模式），不写"修改了某文件"。
- 提交信息里避免内联引号导致的截断；复杂正文用 `git commit -F <file>`。
- 提交前自查：
  ```sh
  npm run check            # 契约检查
  node --check <入口文件>   # 语法
  git status --short       # 无未跟踪残留（临时探针目录要么删掉，要么进 .gitignore）
  ```

## 3. 对外发言的身份

在 GitHub（或任何公开渠道）上执行动作时，**发言者就是仓库所有者本人**—— Issue、PR、评论、提交都署这个账号。因此所有公开文本一律用**维护者第一人称陈述**，而不是"请求某人做事"。

**禁止出现的句式**（会被永久留在公开历史里）：

| 反例 | 问题 |
|---|---|
| "请在合并前于本机重启 DSH 复核" | 所有者请别人复核自己的 PR |
| "需要维护者本机确认……" | 把作者自己的验收外包给不存在的第三方 |
| "请把观察结果回帖" | 把对话当作评审记录 |
| "我来帮你改" / "由 agent 执行" | 暴露内部协作过程，对外无意义 |

**应该写成**：

- 做了什么 + 证据是什么 + 限制是什么 → 陈述句；
- 尚未做到的事：`跟踪于 #N`，而不是"请谁去做"；
- 需要与他人协调的步骤（GUI 点击、重启宿主）：**走对话**，不进 Issue/PR 正文；
- 发布前核对硬事实（提交数、是否已合并、版本号），避免陈述过时状态。

**自检**：发布前搜一遍正文里的 `需要维护者` / `本机确认` / `请把` / `请在` / `帮我` / `由人执行`，命中就改写。（面向外部用户的模板、README 里的"你"是正常的，不要一刀切。）

## 4. Issue 与 PR

### Issue
- **Bug Issue**：现象 → 环境（宿主版本、安装方式、profile、OS）→ 根因（带代码位置，如 `xxx/lib/index.js:1471`）→ 证据（原始命令与输出）→ 修复（指向 PR）→ 临时绕过。
- **功能请求 / 设计缺口**：背景（现状与期望的差距）→ 机制（为什么会这样，带代码位置）→ 期望结果 → 实现路线（可给倾向）→ 待确认项 → 影响范围。
- **下线计划 Issue**：只在本次保留了兼容兜底路径时开。写清：触发条件（如"宿主稳定版 ≥x.y 后 1 个 minor"）、移除清单、通知方式。
- 用仓库的 `.github/ISSUE_TEMPLATE/`（若有）。

### PR
用 `.github/pull_request_template.md`（若有）。八节结构的要点：

| 小节 | 要求 |
|---|---|
| 现象 / 根因 | 根因要落到代码位置，并解释"为什么以前能用、现在不能" |
| 证据 | 贴**真实命令与输出**；凭据、token、remote URL 一律打码。只有当某个对照实验固化了一条必须记住的陷阱时才保留"改前 FAIL / 改后 OK"的对照 |
| 修复 | 改了什么、为什么这样改；保留的兼容路径与下线边界 |
| 验证 | **只列作者能自己完成的项**，逐条勾选 |
| 已知限制 | 无法在本 PR 内消除的限制，写清**是什么 + 为什么**，不留未勾选项 |
| 生效条件 | 何时生效（重载 profile / 重启宿主 / 需重新安装）——这是中性运维事实，不是待办 |
| 风险与兼容性 | 声明面是否最小、版本范围影响、需要用户手工动作的地方 |
| 下线计划 | 若保留兼容路径，写 `Refs #<下线 issue>` |

**验收纪律（重要）**
- PR 里的 `[ ]` 语义是"作者尚未验证"。带着未勾选项提 PR，等于对 reviewer 说"没验完"。
- 需要 GUI 点击、需要重启正在使用的宿主这类**无法在单次会话内完成**的步骤：由作者本人在自己的机器上执行并记录原始观察（命令与输出），写进描述后再勾选、再转出 Draft。确实无法执行时**不要勾选**，把该项连同原因写进「风险与兼容性」，而不是用"不在本 PR 内执行"这类话术代替验收。
- Draft 只用于"尚未开始验收"的短暂时段；验收完成后立即转出：`gh pr ready <n>`。

## 5. 发版

**授权驱动**：发版的唯一前置条件是**所有者明确表示可以发布**（"合并吧" / "发版" / "release" 等）。得到指示后，发布流程由执行者完整跑完，不再逐步请示。

- 未获指示：把改动做到可发布状态（版本号、双语 CHANGELOG、验收证据齐全），**停在合并/发布之前**，并说明当前状态。
- 已获指示：按 [`references/release-checklist.md`](references/release-checklist.md) 执行到底——合并 PR、同步 `main`、打 tag、按渠道发布、发布后核对，逐项留下可核对的结果。
- 合并与 push 到仓库属于常规流程；tag 与对外发布（`npm publish`、市场提交）同样在授权范围内执行。
- 发布中出现阻塞（CI 失败、凭据缺失、平台拒绝）：报告实际状态与失败输出，不要静默重试或跳过步骤。

要点：

1. 递增 `package.json` 的 `version`——插件启动时的更新提示以它为发布标记。
2. 双语 CHANGELOG（`CHANGELOG.md` + `CHANGELOG.zh-CN.md`）同批更新，补版本对比链接。
3. 若改了依赖契约或 peer 范围，确认 `npm run check` 与诊断脚本仍通过。
4. 合并 PR、同步 `main`。
5. 发布后核对：插件页版本号、新会话工具齐备、更新提示按预期出现。

## 6. 通用纪律

- **中文文件不要用 PowerShell 做批量文本替换**。`Get-Content -Raw` + `-replace` + `Set-Content` 这条链路在 PowerShell 5.x 下按 ANSI 解码 UTF-8 文件，**整篇中文会变成乱码写回**，且没有任何报错。批量改文本一律用 Node 脚本（`readFileSync(..., 'utf8')` / `writeFileSync`）。
  - 改完做一次编码自检：正文**不含 `U+FFFD`（替换字符）**，且任取几行中文能正常显示。不要用"是否含有某几个乱码字"来判定——文档里可能正当地举个反例，会误报。
  - 事故代价取决于时机：已提交的文件可 `git checkout -- <file>` 无损还原；**未提交的改动会直接丢失**。改之前先确认目标是否已提交，或先备份/暂存。
- **不要把个人假设写成项目规范**。写入技能/文档的规矩，要么来自仓库既有约定（`CONTRIBUTING`、模板、代码），要么来自所有者明确指示；自己臆测的边界（例如"某类动作永远不由我来做"）会把授权问题误述成能力问题，反而阻碍执行。措辞上区分**授权**（"获得指示后执行 X"）与**禁止**（"永不执行 X"）。
- **证据优先于推断**。同一份判定逻辑要跑在**可比的两组对象**上（例：本插件字段 vs 官方插件同形态字段），否则结论不可靠。自己写的探针先自证：让它对已知正确/已知错误的两组输入给出相反结果。
- **不要用未验证的断言写文档或 PR**。承诺某个 UI/行为前，先确认它在目标版本上真的存在。
- **文档里不要出现装饰性编号**。序号只用于"必须按顺序执行"的清单（从 1 开始）；并列的参考材料、失败模式、配方一律不编号——否则会逼出 `0.`、`0.1` 这类畸形层级。
- **取证输出脱敏**：`git remote -v`、配置片段可能带 token，贴进 issue/PR 前先打码。
- **临时探针**：放在 `.investigate/` 之类已 gitignore 的目录，任务结束即删。
- **公开记录里不留协调痕迹**：临时协议、操作清单、"等某人确认"都不进 Issue/PR（见第 3 节）；事后发现已发出的内容不符合身份要求，**删除或改写**，不要靠后续评论解释。
- **流程变动**（新增检查、新增模板）要同步更新本技能与 `.github/` 模板，避免规范只存在于对话里。
